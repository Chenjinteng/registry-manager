# 产品设计说明

这份文档记录**产品层面的取舍**：每个页面回答什么问题、界面上只留什么、以及
**哪些话刻意不写在界面上**。

它和另外两份文档的分工：

| 文档 | 给谁看 | 写什么 |
| --- | --- | --- |
| `README.md` | 使用者 | 怎么装、怎么配、遇到问题怎么查 |
| `AGENTS.md` | 改代码的人 | 协议实测事实、工程红线、构建约定 |
| **本文件** | 设计与评审 | 为什么这样设计、界面该有什么不该有什么 |

---

## 1. 产品定位

一个**自成一体的小工具**：浏览和管理**一个** CNCF Distribution registry 里的镜像。

刻意不做的事（都是产品决定，不是未完成项）：

- **没有登录、没有多实例** —— 一次管一个 registry；
- **没有需要运维的数据库服务** —— 热度统计用 Node 自带的 SQLite，落一个文件；
- **不进数据面** —— 镜像字节永远不经过本工具，它只是控制面。

## 2. 界面文案的规矩

> **界面上只写"这里能做什么"，不写"为什么这么实现"。**

这条是**硬规矩**，原因是两个，都不是审美洁癖：

1. **原理不该出现在产品上**。使用者关心的是"这个页面能干什么"，
   不是 `AES-256-GCM`、`webhook`、`manifest HEAD` 这些内部机制。
   把实现细节摆到台面上，等于要求使用者先读懂源码才能用工具。
2. **它会漂移**。界面文案上的实现细节不会随着代码一起被更新，
   最后变成一句看起来权威、实际已经过时的说明 —— 比没有更糟。

原理写到 **`README.md`**（面向使用者解释）和 **本文件**（面向设计解释），
界面上最多留一句"这是什么页面"。

### 每个页面的副标题只保留一句

| 页面 | 副标题 |
| --- | --- |
| 镜像列表 | 浏览并管理 registry 中的镜像。 |
| 镜像热度 | 统计每个仓库与 tag 被推送、拉取的次数。 |
| 镜像拉取 | 像 `docker pull` 一样贴一个镜像名就可以拉取。 |
| 凭据管理 | 管理外部 registry 的 basic auth 凭据。 |
| 代理管理 | 管理访问外部源时使用的 HTTP 代理。 |
| 设置 | 当前管理的镜像仓库、连接状态与清单缓存。 |

**操作指引**（例如"源在受限网段时去高级选项填代理"）可以留在副标题里 ——
它告诉使用者"现在该做什么"，和"为什么这么实现"是两回事。
**需要使用者先理解机制才能看懂的解释，一律移出界面。**

## 3. 被移出界面的三处原理

以下三段曾经写在页面副标题上，现已移除。它们的正式归宿就是这里和 `README.md`。

### 3.1 为什么本仓库自身的凭据不在这里配

凭据与代理按**作用对象**分成两处，是刻意的：

| | 配在哪 | 为什么 |
| --- | --- | --- |
| **本 registry 自身** | `registry.config.json` / `REGISTRY_USERNAME`、`REGISTRY_PASSWORD`、`REGISTRY_PROXY` | **部署级**：没有它连「镜像列表」都打不开，服务启动时就必须具备；作用于所有对本仓库的请求，所以没有"每任务选一次"的意义 |
| **外部源** | 页面上的「凭据管理」/「代理管理」 | **任务级**：同一个源会拉很多次，也可能有多个源；放进可增删改的库里，任务里按需选用 |

因此任务表单里只有**源**认证与**源**代理。详细的对照表见
[README 的「认证 / 代理怎么配：都分两处，不要混」](./../README.md)。

### 3.2 加密落盘与密钥丢失

凭据库与代理库用 **AES-256-GCM** 加密后落盘，密钥由 `REGISTRY_CREDENTIAL_KEY`
经 scrypt 派生。

> **密钥与文件同时丢失 = 永久不可恢复。**

这是 AES-GCM 的固有限制，不是实现缺陷。备份时两者必须一起带走。
这句话在 `README.md` 与 `AGENTS.md` 里都保留着 —— 它足够重要，
但**不放在页面上**：使用者不需要在每次打开凭据页时被提醒一次密钥管理策略。

### 3.3 热度的统计口径
界面上的数字是「**镜像被用了多少次**」，不是流量。

口径（全部来自真实 registry 的实测，详见 [`pull-heat.md`](./pull-heat.md)）：

```
action == "pull" | "push"
AND target.mediaType 属于 manifest 家族      → 排除 blob（一次 pull 十几条）
AND request.method ∈ {HEAD, PUT}            → 排除按 digest 的 GET（与 HEAD 同一次拉取）
```

三个条件缺一不可：只按 `action` 过滤会把 `docker push` 的 blob 探测算成拉取；
不滤 blob 会让热度被镜像层数放大十几倍。

**为什么这个解释不放页面上**：它是内部实现细节。使用者需要知道的只有一句 ——
"这个数字是次数，不是流量"，而这一句写在 `README.md` 的「怎么算"一次拉取"」里。

## 4. 数据存放在哪

判据有两条，缺一不可：**① 需不需要跨重启活下来？② 关系型是否真的更好？**

| 数据 | 存在哪 | 为什么 |
| --- | --- | --- |
| 热度统计 | SQLite（`data/registry-manager.db`） | 按天预聚合的计数；append-only、按时间查，天然适合 |
| 拉取历史 | SQLite（**同一个库**） | 同上；运行态留内存，只有终态落库 |
| 凭据 / 代理 | 整份 AES-256-GCM 加密的**独立 JSON** | 进表**会变差**，见 §4.1 |

### 4.1 凭据与代理为什么不进 SQLite

进表的话，自然的 schema 是：

```sql
CREATE TABLE credentials(id, name, registry_url, username, password BLOB, ...)
```

于是 `name` / `registry_url` / `username` **全是明文**，只剩密码加密 ——
拿到文件就能知道"有几个凭据、指向哪些 registry、用户名是什么"。
现在的整份加密只暴露**文件大小**。这是实打实的强度差别，不是风格偏好。

另外两条同样重要：

- **敏感等级要分文件**。`registry-manager.db` 装的是非敏感的统计与任务历史，
  谁都能备份、传阅。凭据进去之后，"把 db 发给同事看看"就变成泄密操作，
  而且丢一个文件同时丢统计和凭据。README 里那句"密钥与文件同时丢失 = 不可恢复"
  正好只覆盖那两个文件，边界是清楚的。
- **数据量是个位到几十条**，SQL 的查询能力在这里没有意义。

### 4.2 拉取历史为什么进，以及运行态为什么不进

**进**：历史必须跨重启活下来（"上周搬了哪些镜像"重启一次就答不了），
而它天然是 append-only、按时间查询的日志，和热度同形，保留期机制也是现成的。

**只写终态**：`queued` / `running` 需要高频更新，且只在进程活着时有意义；
把半截数据固化进历史没有价值，还会让它看起来像一份完整的记录。

**阶段明细只在失败 / 取消时写**：一次 20 层的拉取有 22 条 phase，
成功的任务存它只会把行撑胖，而没人会去看成功任务的分层进度。

**保留期与热度分开配置**（`REGISTRY_PULL_HISTORY_RETENTION_DAYS` 与
`REGISTRY_STATS_RETENTION_DAYS`）：两者的价值周期不一样。
代码里也是两个独立方法（`cleanup` / `cleanupPullJobs`）——
合在一起迟早会把其中一个的保留期套到另一个头上。

## 5. 界面结构的取舍

- **导航在顶部**，不做左侧栏：这是个小工具，页面数量少，顶部横向切换更快。
- **只有表格区域滚动**（镜像列表、热度榜单）：翻表格和改筛选条件是交替发生的动作，
  整页滚动会让搜索框、时间窗、KPI 一起被顶走。
- **热点图表手写 SVG，不引图表库**：需求很窄（单序列按天），
  为它引一整个图表引擎与"小到能看懂"的定位冲突。
- **未启用时的空状态要给配置片段**：热度依赖 registry 侧的 `notifications`，
  使用者不配就永远看不到数据。空状态里直接给出可复制的 YAML，
  比一句"未启用"有用得多。
- **维护类 / 不可撤销的动作放「设置」页，不放在日常操作旁边**：清空热度数据是一次性的
  口径维护动作，放在热度页的时间窗与「刷新」旁边迟早被误点 —— 那两个按钮是天天要按的。
  同理，"删除"这类破坏性操作前必须写清后果，而不是只给一个红色按钮。

### 5.1 深浅主题为什么这么实现

界面上只放一个按钮（切换 + 记忆选择），实现细节都在这里。

- **两套 token，靠 `<html data-theme>` 切换。** `web/src/theme.css` 的 `:root` 是浅色、
  `[data-theme='dark']` 是深色，**必须一一对应**。漏掉的那个 token 会继续用浅色值，
  表现为"某个角落突然是白的"，而且不报错、不抛异常、type-check 也过。
  `pnpm verify:theme` 就是把这条对应关系变成断言。圆角这类与主题无关的 token 明确豁免
  —— 逼它们各写一遍只是徒增两处漂移点。
- **深色不是把浅色取反。** 同一个色值在深色底上的对比度、饱和度感受完全不同：
  主色要提亮（`#155aef` → `#4c8dff`，原来的蓝压在深色底上发闷），
  文字要用低饱和冷灰，层级靠"比背景亮一点"分层而不是靠深色描边。
- **AntD 必须跟着一起变，否则会"半深色"。** 我们自己的 CSS 变深了、AntD 的表格 / 分页器 /
  下拉 / 标签还是浅色，同一屏里两套配色 —— 这是深色主题最常见的翻车方式。
  深色以 AntD 的 `darkAlgorithm` 打底（它负责上百个我们没显式列出的派生色：
  禁用态、hover、阴影边界），**再把语义色对齐到 `theme.css` 的深色值**。
  两边必须是同一组值，否则会出现两种不同的蓝；`pnpm verify:theme` 逐个比对这些色值，
  `pnpm verify:layout` 再用真实浏览器读每个"面"的 computed style。
- **刷新不能闪白。** 主题是 `documentElement` 上的一个属性，如果等 React 起来再设，
  首帧会先按浅色渲染一次。所以设置在 `web/index.html` 的**内联脚本**里，
  它同步执行、早于模块脚本；React 侧**只读**这里的属性，不再重复判断系统偏好
  —— 两处判断就是两个真相来源，迟早不一致（而且那正是首屏闪烁的根源）。
  读取顺序"上次的选择 > 系统偏好"只写一份。
- **`color-scheme` 两套都要设。** 否则原生滚动条、表单控件、`<select>` 弹层
  不跟随主题，深色页面上会插着一根亮滚动条。

## 6. 如何验证这些设计真的落地了

- 界面文案是否只剩"能做什么"：**人工走查**（没有自动检查，因为这是判断而非规则）。
- 布局是否符合预期：`pnpm verify:layout`（无头 Chrome 真的滚一遍并截图），
  其中包含深色主题的浏览器断言：真点按钮、真读 computed style、刷新后检查首帧。
- 深浅两套 token 是否对应、引用的 token 是否存在、AntD 色值与语义 token 是否一致：
  `pnpm verify:theme`（含**回退验证**）。
- 热度口径是否正确：`pnpm verify:stats`（含**回退验证**，确认断言挡得住回归）。
- 拉取历史的存储契约（迁移不丢数据、只记终态、保留期互不干扰）：
  `pnpm verify:pull-history`。
